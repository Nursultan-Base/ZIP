# PRD: Учёт получения ЗИП

**Продукт:** веб-приложение для регистрации и отчётности по приёму ЗИП (запасные части, инструменты и принадлежности)
**Заказчик:** ТОО «Оптиктелеком СтройСервис», Отдел ИТ и связи
**Подготовил:** Нарымбетов Н.Б., начальник отдела ИТ и С
**Статус документа:** черновик, сформирован по итогам обсуждения в чате
**Дата:** сентябрь 2026

---

## 1. Проблема и контекст

Отдел ИТ и связи ежеквартально подаёт заявку на ЗИП (запасные части, инструменты и принадлежности) по нескольким направлениям — ВОЛС, УКВ РРЛ, АТС, КЛС. На 2-й квартал 2026 года заявка включает 24 позиции. Учёт того, что фактически поступило по заявке — какими партиями, от какого поставщика, по какому акту, куда оприходовано и где хранится — велся не в едином инструменте. Из-за этого сложно:

- быстро увидеть, какие позиции заявки ещё не закрыты и на какой остаток;
- сформировать отчёт/акт о поступлении ЗИП за период для руководства или бухгалтерии;
- проследить, куда именно ушли полученные материалы.

## 2. Цель продукта

Дать отделу ИТ и связи простой инструмент для регистрации каждого поступления ЗИП и автоматического формирования отчётов, без необходимости вести это вручную в Excel и без внедрения серверной инфраструктуры.

## 3. Пользователи

- **Основной пользователь:** начальник отдела ИТ и С (Нарымбетов Н.Б.) — ведёт заявку, регистрирует приём, формирует отчёты.
- Косвенно — руководство/бухгалтерия ТОО, которым передаются отчёты и акты в печатном или CSV-виде.

Приложение однопользовательское, без ролей и авторизации.

## 4. Пользовательские сценарии

**Сценарий 1. Регистрация планового поступления**
Начальник отдела получает партию ЗИП по заявке. Открывает вкладку «Приём ЗИП», выбирает соответствующую позицию заявки из списка (услуга, наименование и единица измерения подставляются автоматически), указывает фактическое количество, дату, поставщика и номер акта. После сохранения остаток по этой позиции в разделе «Заявка» уменьшается автоматически.

**Сценарий 2. Внеплановое поступление**
Поступил материал, не входивший в квартальную заявку. Пользователь регистрирует приём без привязки к заявке, заполняя все поля вручную.

**Сценарий 3. Формирование отчёта за период**
В конце месяца или квартала пользователь открывает вкладку «Отчёт», задаёт диапазон дат и при необходимости фильтрует по услуге или поставщику. Далее либо выгружает данные в CSV для бухгалтерии, либо распечатывает отчёт в виде акта с местом для подписи.

**Сценарий 4. Резервное копирование и перенос данных**
Пользователь скачивает файл `.db` как резервную копию или для переноса на другое устройство, где позже загружает этот файл через «Загрузить .db».

## 5. Границы (scope)

### Входит в текущую версию
- Ведение квартальной заявки на ЗИП (список позиций с планом по количеству).
- Регистрация фактического приёма ЗИП с привязкой к позиции заявки.
- Автоматический пересчёт остатка по заявке при регистрации приёма.
- Отчёт с фильтрами (дата, услуга, поставщик), экспорт в CSV, печать в виде акта.
- Экспорт и импорт данных в виде файла базы SQLite (`.db`).

### Не входит в текущую версию
- Многопользовательский доступ, роли, авторизация.
- Серверный бэкенд, синхронизация между устройствами/сотрудниками.
- Уведомления, сроки поставки, работа с поставщиками как отдельными сущностями.
- Печать первичных бухгалтерских документов по установленной форме (только отчёт/акт в свободной форме).

## 6. Функциональные требования

### 6.1 Обзор (Dashboard)
- Сводные показатели: количество позиций в заявке, количество записей о приёме, число открытых (не закрытых полностью) позиций, число поступлений за текущий квартал.
- Разбивка выполнения заявки по услугам (ВОЛС, УКВ РРЛ, АТС, КЛС, Прочее) — доля полученного от заявленного в процентах.

### 6.2 Заявка
- Добавление позиции заявки: услуга, наименование, единица измерения, заявленное количество, примечание.
- Таблица позиций с расчётными полями «получено» и «остаток»; остаток пересчитывается автоматически на основе связанных записей приёма.
- Удаление позиции заявки (связанные записи приёма при этом теряют привязку, но не удаляются).

### 6.3 Приём ЗИП
- Форма регистрации поступления: необязательная привязка к открытой позиции заявки (с автозаполнением услуги/наименования/ед. изм.), количество, единица измерения, дата получения, поставщик, № акта/документа, место хранения, куда/на что использовано, примечание.
- Список последних записей о приёме с возможностью удаления.
- Приём можно регистрировать и без привязки к заявке (внеплановое поступление).

### 6.4 Отчёт
- Фильтры: период (дата с/по), услуга, поставщик (поиск по подстроке).
- Табличный вывод по всем полям записи приёма.
- Экспорт отфильтрованных данных в CSV (с BOM для корректного отображения кириллицы в Excel).
- Печать отчёта в виде акта: скрывает элементы управления, добавляет блок подписи («Составил», дата).

### 6.5 Управление базой данных
- Кнопка скачивания текущей базы данных целиком в виде файла `.db`.
- Загрузка (импорт) стороннего файла `.db`, полностью заменяющего текущие данные, с подтверждением действия.

## 7. Модель данных

Реляционная схема из двух таблиц.

**request_items** (позиции заявки)

| Поле | Тип | Описание |
|---|---|---|
| id | TEXT, PK | идентификатор |
| service | TEXT | услуга: ВОЛС / УКВ РРЛ / АТС / КЛС / Прочее |
| name | TEXT | наименование |
| unit | TEXT | единица измерения |
| qty | REAL | заявленное количество |
| note | TEXT | примечание |
| created_at | TEXT | дата создания записи |

**received_items** (записи о приёме)

| Поле | Тип | Описание |
|---|---|---|
| id | TEXT, PK | идентификатор |
| request_item_id | TEXT, nullable | ссылка на позицию заявки (может отсутствовать) |
| service | TEXT | услуга |
| name | TEXT | наименование |
| qty | REAL | полученное количество |
| unit | TEXT | единица измерения |
| date_received | TEXT | дата получения |
| supplier | TEXT | поставщик |
| act_number | TEXT | № акта/документа |
| storage_location | TEXT | место хранения |
| purpose | TEXT | куда/на что использовано |
| notes | TEXT | примечание |
| created_at | TEXT | дата создания записи |

Остаток по позиции заявки = `qty` заявки минус сумма `qty` всех связанных записей `received_items`.

## 8. Техническая реализация

- Приложение — самодостаточный HTML/CSS/JS-файл (артефакт), без серверной части.
- База данных — SQLite, выполняемая в браузере через WebAssembly (sql.js, версия 1.14.2, подключается с cdnjs).
- Хранение между сессиями — бинарный файл SQLite сохраняется в персистентное key-value хранилище артефакта (в виде base64), поскольку у среды выполнения нет доступа к серверу или файловой системе пользователя.
- Экспорт/импорт `.db` позволяет переносить данные в сторонние инструменты (например, DB Browser for SQLite) или использовать как отправную точку для будущего серверного решения.
- Данные не покидают браузер пользователя — нет передачи на внешние серверы.

## 9. UX и визуальный стиль

- Стилистика «технического журнала/реестра»: шапка-«бланк» с названием компании, вкладки в виде закладок, табличная вёрстка с тонкими линиями.
- Шрифты: IBM Plex Serif (заголовки), IBM Plex Sans (текст), IBM Plex Mono (числа, коды, данные).
- Цветовая палитра: тёплый серо-бежевый фон, стальной синий как акцентный цвет, янтарный — для незакрытых позиций, зелёный — для выполненных.
- Адаптивность под мобильные экраны, печатная версия скрывает элементы управления и формы.

## 10. Критерии успеха

- Все позиции квартальной заявки внесены и отслеживаются в приложении, остаток виден в реальном времени.
- Формирование отчёта о поступлении ЗИП за период занимает минуты вместо ручного сведения данных в Excel.
- Ни одна запись о приёме не теряется между сессиями работы в одном браузере.
- Отчёт и акт можно передать бухгалтерии/руководству без дополнительной обработки данных.

## 11. Риски

- **Хранение только в браузере одного устройства.** При очистке данных браузера или переходе на другой компьютер без предварительного экспорта `.db` информация будет потеряна. Снижение риска — регулярный экспорт `.db` как резервной копии.
- **Однопользовательский режим.** Если приём ЗИП со временем начнут регистрировать несколько сотрудников одновременно, потребуется переход на серверную архитектуру (см. раздел 13).
- **Зависимость от внешнего CDN.** Библиотека sql.js загружается с cdnjs при каждом открытии приложения — без интернета приложение не запустится, даже если данные уже сохранены локально.

## 12. Ограничения текущей версии

- Однопользовательский режим: нет разделения доступа между сотрудниками и синхронизации между устройствами.
- Объём хранимых данных ограничен лимитом хранилища артефакта (≈5 МБ на ключ), для текущих объёмов ЗИП этого достаточно с большим запасом.
- Нет автоматического резервного копирования, кроме ручного экспорта `.db`.
- Исходный список 24 позиций заявки на 2-й квартал 2026 года не был доступен в структурированном виде на момент разработки — позиции заявки вводятся пользователем вручную через раздел «Заявка».

## 13. Возможные направления развития

- Перенос на серверную архитектуру (например, SQLite на сервере) для многопользовательского доступа и синхронизации между сотрудниками отдела.
- Печать отчёта по установленной бухгалтерской форме акта.
- Учёт поставщиков как отдельного справочника с историей поставок.
- Уведомления о позициях заявки, которые давно не закрываются.

## 14. Открытые вопросы

- Нужен ли многопользовательский доступ в обозримой перспективе, или однопользовательского браузерного решения достаточно?
- Требуется ли отчёт в конкретной унифицированной форме акта приёма материальных ценностей?
- Нужна ли интеграция с уже используемой бухгалтерской системой ТОО?
